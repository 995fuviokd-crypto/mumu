# 追加结论：为什么“检测全部通过”做不到

日期：2026-11-21（承接 Momo-Crash-Analysis.md）

## 实测链路

1. **原版签名**：native `App.get(20)` 返回通过码 → 检测继续 → UI 协程调用 `App.check()` → 解密表为空 → SIGSEGV（1 秒内必崩）。
2. **重签后**：`App.get(20)` 返回异常码 → `Ei` 构造 `Fi(<code>)` → UI 显示“环境损坏 / 签名验证失败”，并**停止后续检测**。
3. **仅绕过 Java 证书哈希比对**（`Ei` 中 `cert.hashCode()` 与常量 `-0x1456f89e` 比较）不够：强行走证书分支后改为报
   “检测到破坏行为（例如 MagiskHide），其他检测无法继续”——加固库的**完整性/反篡改判定**，APK 被改过就命中。
4. 闭环：
   - 不改包 → 干净分支 → `check()` 空表崩溃；
   - 改包（任意 dex/so 改动或重签）→ 反篡改判定 → 检测中止。

## 已逐项排除的环境项

| 项 | 结果 |
| --- | --- |
| qemu / vbox / hv 属性 | 无效 |
| 安全补丁日期（含 Build 缓存问题） | 无效 |
| SELinux Permissive → Enforcing | 无效 |
| ABI x86_64 / arm64（houdini） | 均崩 |
| APK 内加载 vs 真实 .so 文件加载 | 均崩 |
| READ_LOGS 授权 | 无效 |
| 连续 5 次冷启动（竞态） | 100% 同一 PC |
| 强制 native 状态码通过 | 进入“破坏行为”判定 |
| 绕过 Java 证书比对 | 仍被原生完整性判定拦截 |

## 结论

- “全部通过”要求 Momo 认可一个**被修改过的检测工具**，与其反篡改设计直接冲突；不伪造检测结果就无法在这台模拟器上得到全绿。
- 不伪造结果时能做到的是：让它打开并显示真实信息（当前“重签版”即为此状态：显示系统指纹、安全补丁级别等，同时如实报告 APK 已被改签）。
- 若坚持原版签名运行，只能依赖运行时注入（Frida / LSPosed / Zygisk）在 `check()` 前调用 `App.get(0)`；但 Momo 内置 XposedDetector / NativeDetector，注入框架本身大概率被判定为“破坏行为”，仍不能保证全绿。
